Getting Started

Required: Claude Pro or higher. Pro is the cheapest plan that includes Claude Code and the desktop app (see current prices). For a workshop it's simpler and better value than buying API credits. The Free plan isn't enough.

The backlog is ready: ten user stories for the X Clone, grouped in four epics, with the PRD behind them, are waiting on the team's board. Like a developer joining the team, you take it from there. You build a small team of Claude Code skills that take a story from New to In Acceptance on their own, checking their work with end-to-end tests and posting a video for every acceptance criterion. The only human step is yours: accepting the work on the board.

Plan Mode — Think Before You Code
Use Plan Mode to design your approach before writing code
~10 min
  1. Enter Plan Mode — press Shift+Tab to cycle the mode indicator until it reads plan mode on.

    Plan Mode tells Claude to research and design an approach WITHOUT making any changes. It explores the codebase, reads relevant files, and proposes a step-by-step implementation plan. You review the plan and only then approve it for execution.

    Use it whenever a feature touches 3+ files or involves non-obvious logic.
  2. Plan a hypothetical feature — nothing here gets built for real, this is just to practice the workflow:
    Prompt (in plan mode)
    I want to add a "Bookmarks" feature: a bookmark toggle on each tweet, and a new route showing everything the current user has bookmarked. Plan the approach — which files you'd touch on the frontend, where the bookmarked-state would need to live, and how the route would fetch the list. Don't write any code yet.
  3. Review the plan — Claude will propose:

    Which files to modify, what components/hooks to create, and the data flow. Ask questions, request changes, or approve when satisfied.

  4. Exit Plan Mode — When you're happy with the plan, approve it. (Pressing Shift+Tab again also leaves plan mode.)
    Once you approve, Claude executes the plan and makes the actual code changes — you're welcome to stop before that step, since this exercise is just for practice.

Guardrail Hooks — Block Risky File Access
Stop Claude reading secrets or editing generated files
~10 min

Hooks are commands Claude Code runs automatically on lifecycle events, with no model involved. They live in .claude/settings.json and receive a JSON payload on stdin. Before we build anything, let's use them as guardrails — a PreToolUse hook can inspect a tool call and block it, giving you a hard guarantee that a scoped rule can't. We'll write them as small Node scripts so they run on every machine — macOS, Linux, and Windows — with no jq and no shell quirks. (Hooks, skills and subagents are the three extension points; you build skills and a subagent in Part 3.)

1. PreToolUse — don't read secrets
Prompt
First use the claude-code-guide agent to check the documentation on how to create hooks. Then add a PreToolUse hook that blocks Claude from reading secret files like .env, .env.local, and .env.production, with a clear reason — but still allow the safe .env.example template. Write it as a cross-platform Node script so it runs on macOS, Linux, and Windows.
2. PreToolUse — don't write lockfiles or generated files
Prompt
First use the claude-code-guide agent to check the documentation on how to create hooks. Then add a PreToolUse hook that blocks Claude from editing lockfiles and generated files like src/frontend/pnpm-lock.yaml and src/frontend/src/routeTree.gen.ts, with a reason explaining it's a lockfile or a generated file. Write it as a cross-platform Node script so it runs on macOS, Linux, and Windows.
Why Node + exec form? Setting "command": "node" with an args array spawns the script without a shell, and Claude Code substitutes ${CLAUDE_PROJECT_DIR} itself — so the same hook runs identically on macOS, Linux, and Windows, with no jq, Git Bash, or WSL. A shell one-liner would need a POSIX shell on Windows.
Hooks run code as you — only add hooks you trust. The Read guard covers the Read tool; Claude could still cat .env via Bash, so for airtight secrets also use Claude Code's built-in permissions.deny (e.g. "Read(./.env)"). Run /hooks to see what's active.
Reference: the .claude/settings.json (exec form)
.claude/settings.json
{ "hooks": { "PreToolUse": [ { "matcher": "Read", "hooks": [ { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/deny-read-env.mjs"] } ] }, { "matcher": "Edit|Write", "hooks": [ { "type": "command", "command": "node", "args": ["${CLAUDE_PROJECT_DIR}/.claude/hooks/deny-write-protected.mjs"] } ] } ] } }
  • Reading .env is blocked with a clear reason
  • Editing pnpm-lock.yaml / routeTree.gen.ts is blocked
  • Hooks run unchanged on your OS (exec form, no jq)

Build /implement-story
Tests first, then code, until everything is green
~20 min

The first stage skill. It reads one story, writes a Playwright test for each acceptance criterion (AC1: …, AC2: …), then builds the code and runs the checks until they pass. Like every skill today, it's a folder: a SKILL.md plus the reference files it needs, here how to talk to the board.

Prompt

Write each one with exactly this content (the ==== lines only show where each file starts; don't write them into the files): ==== SKILL.md ==== --- name: implement-story description: Build one story from the board, test-first: a Playwright test per acceptance criterion, then the code, looping until every test is green. Moves it New → In Progress → In Review. argument-hint: <story key, e.g. XC-5> --- # Implement a story Builds one story so that every acceptance criterion is proven by a test and nothing that already worked breaks. Usage: `/implement-story <KEY>`. Run from the repository root. ## References (in this skill's own folder) - `reference/board-api.md`: how to move a ticket and comment on it. ## Steps 1. **Find the story.** Look up `<KEY>` in `docs/tracker/board-data.js`, then open its heading in `docs/stories/` (the item's `source`). Read its acceptance criteria, its `Covers` IDs and the PRD lines they point to, including the PRD's Non-Functional Requirements and Out of Scope. If the key isn't on the board, stop and say so. If the ticket is In Acceptance or Done, stop: there's nothing to build. 2. **Start.** Move the ticket to **In Progress** and comment `Started` with the commit you start from (`git rev-parse --short HEAD`). That commit is the story's base: the review compares against it. 3. **Write the tests first.** Create `src/frontend/e2e/<key>.spec.ts` (key in lower case, for example `xc-5.spec.ts`). Write one test per acceptance criterion, named `AC<n>: <the criterion in a few words>`, in the criterion's order. Import `test` and `expect` from `./fixtures`. Wrap each user action in `evidence.step("…", …)` with a short caption: the QA videos show these. Each test must check what its criterion says, not something easier. 4. **Build.** Change the app in `src/frontend/src/` following `CLAUDE.md`: reuse `components/ui/` and the `queries/` pattern, and keep the existing code style. Add Vitest tests for any logic you add. Never edit generated files or the story text. 5. **Verify.** From `src/frontend` (dev server running, sign-in saved with `pnpm e2e:login`), run `pnpm exec tsc -b`, `pnpm lint` and `pnpm e2e e2e/<key>.spec.ts`. Fix the code and run them again until all three pass. Stop after 5 tries and report what blocks you. 6. **Hand over.** - **Green:** commit with the message `<KEY>: <story title>`. Move the ticket to **In Review** and comment: the files changed, each check and its result, and anything a reviewer should look at. - **Stopped:** leave the ticket **In Progress** and comment what blocks it and the last failing output. Don't commit broken work. ## Rules - Never weaken, skip or delete a test to get green. Change a test only when it is wrong about its criterion, and say so in the hand-over comment. - Never move a ticket past In Review. Review, QA and acceptance are other steps. - No scratch, probe or debug files anywhere in the repo. - **Unattended** (run by `/implement`): ask nothing. Tips, Tricks & Resources

Useful patterns, keyboard shortcuts, and links to keep learning.

Tips & Tricks

Prompting

  • Be specific about files — "In src/frontend/src/routes/_app/index.tsx, add a bookmark button" works better than "add a bookmark button somewhere".
  • Ask Claude to check the actual API response — the Swagger reference covers the shape, but hitting the endpoint and showing Claude the real response before writing code against it still catches surprises Swagger won't.
  • Iterate, don't restart — If Claude gets something wrong, tell it what's wrong in the same conversation. It has full context of what it just did.
  • Paste error messages — Copy-paste the full error. Claude is great at diagnosing stack traces and TypeScript errors.
  • Use screenshots — a failed Playwright test leaves a screenshot and an error-context.md under test-results/: point Claude at them.

Workflow

  • Plan Mode for complex features — Use Shift+Tab to toggle Plan Mode before starting a multi-file feature. Review the plan, then toggle back to execute.
  • One feature per conversation — Start a new conversation (/clear) between features to keep context clean and focused.
  • Compact long conversations — If a conversation gets long, use /compact to summarize the history and free up context space.
  • Let the agent cook — For big features, give Claude the full requirements and let it work. Review the result rather than micromanaging each step.
  • Use agents for different hats — the reviewer in /review-pr sees only the diff and the story, never the builder's reasoning: that's what makes it a second opinion.

Keyboard shortcuts

  • Shift+Tab — Toggle Plan Mode
  • Esc — Cancel current generation
  • Tab — Accept Claude's suggestion
  • Ctrl+C — Exit Claude Code

Useful links

  • Claude Code Documentation — Official docs covering installation, configuration, CLAUDE.md, MCP servers, agents, and more
  • Anthropic Skilljar Courses — Free courses on prompt engineering, Claude best practices, and building with Claude
